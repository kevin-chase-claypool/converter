# Use a fast nominal preview with exact compensated G-code

## Summary

Interactive preview now uses nominal machine X/Y by default when bed
compensation is active. Saved G-code continues to use the selected profile
exactly. A new **Exact compensated preview (slow)** option restores full
preview/saved-coordinate parity when needed.

## Reason

The combined CMYK preview from the 2026-10-23 session contained 8,699 contours
and 740,846 points. With compensation enabled, `build_preview_moves` remained
active after several minutes; with compensation disabled the full move build
took 2.6 seconds. A reduced 100-contour sample took 0.063 seconds without
compensation and 4.891 seconds with it.

The cost was not extra geometry: the sample produced 7,869 moves without
compensation and 7,871 with it. Nearly all of the slowdown came from
`compensation_step_count`, which evaluated the full local-affine profile 16
times per source segment to decide whether subdivision was needed.

## Implementation

- `build_preview_moves` accepts `apply_compensation`; the fast path uses the
  nominal machine transform and never calls `compensation_step_count`.
- `PreviewWorker` no longer generates the complete G-code listing during an
  interactive preview. Preview now returns simulation moves only; G-code is
  generated by the normal Convert or multi-file save path.
- Added **Machine > Exact compensated preview (slow)**, default off. When
  enabled, preview moves run through the same compensation lookup and
  subdivision as exact preview output.
- The status bar and log identify nominal versus exact preview, including the
  active compensation fingerprint.
- `contours_to_gcode` remains fully compensated and continues to record the
  profile fingerprint in the file header.

## Verification

- The original 8,699-contour CMYK combined preview now completes its three
  measured stages in approximately `1.1 s` read + `3.7 s` plan + `2.6 s` fast
  preview moves in the headless equivalent. Before the change, compensated
  preview move construction had not completed after several minutes.
- A reduced deterministic 100-contour comparison measured `0.063 s` with
  compensation off versus `4.891 s` with it before the fast-preview change;
  the new path structurally verifies that no compensation probes are called.
- Existing exact preview/G-code parity tests remain in place and pass when
  exact preview is requested.
- The bed-compensation/photo suite passes all `29` tests, and the full converter
  suite passes `488` tests with one OpenGL-context skip. The UI regression also
  confirms exact preview is off by default and reaches the settings model when
  enabled.
- A direct offscreen `PreviewWorker` run completed with an empty preview-time
  G-code string and reported `preview_compensated: False` while preserving the
  active profile fingerprint `4c8270de8a74`.

## Struggles and rejected approaches

- Removing compensation only from the G-code was rejected because the saved
  output must retain the measured correction.
- Silently showing nominal coordinates as exact was rejected. Fast preview is
  identified in both the status bar and log.
- Replacing the expensive compensation probe outright was deferred because it
  needs a separate correctness analysis of how a smooth correction field can
  be bounded without 16 full interpolations per segment.

## Risks and follow-up

- Fast preview can differ from saved G-code by the local compensation vector;
  the current profile has a maximum correction of about `1.33 mm`. Use exact
  preview when inspecting machine-coordinate placement or motion verification.
- Exact preview and G-code generation can still be slow on dense artwork until
  the compensation probe/lookup is optimized.
- The fast preview is intentionally approximate for visualization and motion
  review, not evidence of the final compensated coordinate path.
